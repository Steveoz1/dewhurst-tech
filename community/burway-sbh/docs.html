Firebase capacity: the free plan is not enough for race day

The limit is per day. Firebase's free (Spark) plan allows 50,000 document reads a day. The count resets around midnight Pacific time, which is 08:00 UK time, so the whole of race day falls within one day's allowance.

How the pages use reads. Opening the Results page costs about 3 reads (crew list, settings, instance A times). While the page stays open, every change to any A time costs one more read per open page, because all of A's times are held in a single record. With up to 200 crews, that is roughly 400–500 changes over the day.

Expected use. Up to 200 crews with perhaps 5–10 supporters each gives around 2,000 people. At 25 views each that is 50,000 page opens, or about 150,000 reads before live updates, which could add as much again. The estimate is therefore 150,000–300,000 reads, three to six times the free allowance. Timing writes number only a few thousand, well within the separate allowance of 20,000 writes a day.

If the allowance runs out. On the free plan, reads are refused once the allowance is used, at least until the next reset. Results would stop updating for the public, and the officials' pages would stop receiving each other's times. Taps would still be saved, because writes have their own allowance, but the A/B check and Results would go dark mid-race.

Decision: move to the pay-as-you-go (Blaze) plan before race day. Blaze keeps the same free allowance, then charges about $0.03 per 100,000 reads, so even 1 million reads costs well under £1. A budget alert (for example £10) sends an email but doesn't stop anything. The upgrade needs a payment card and is made in the Firebase console: project burway-sbh-2026 › “Spark” (bottom left) › Upgrade › Blaze, then add the budget alert. No change to the site is needed.

Race Adjudication: how it works0 / 14

How the A/B check works. Toggles on the 6 points to confirm and the J-tests.

Written: Thu 22 Oct 2026. A plain-English guide to the Race Adjudication page: what each part does, what the adjudicator should see, and how to test it. Governing requirements: design brief F-K7 (adjudication changes), F-R8 (A/B check), F-R12 (the "Needs a look" rules and Resolve). This document explains them; it doesn't add to them. Section 5 lists the points to be confirmed before race day.

1. The idea in five lines

  1. Two independent sets of times. A and B are timed by different people on different phones. A is the official record, and the only one the public sees. B is the check copy.
  2. The page compares A and B for every crew and lists any crew where they disagree under Needs a look (the rules are in section 3 and in the expandable list on the page).
  3. The adjudicator decides which is right. Either A is already right, so the adjudicator taps Resolve. Or A is wrong, so the adjudicator changes A (usually by copying B's time, or by typing the right time) and the difference disappears.
  4. Every change needs a reason, and is added to the crew's tap list. Nothing is ever deleted; the original taps stay underneath.
  5. A crew is finished with when it no longer appears under Needs a look: either because A and B now agree, or because it has been resolved.

2. The screen

Main table — one row per crew: A start / finish / time / position, then the same for B, then A−B (the difference in race time, for information), Flags, and two buttons:

  • Review opens the crew's Review window (section 4).
  • Resolve (only on crews with flags) means "this crew has been checked and A is correct as it stands".

Needs a look / All crews switches between only the crews with unresolved flags and every crew.

3. When a crew "needs a look" (F-R12)

# Flagged when… Shown as Colour
1 A and B both have a start, more than 1.0 s apart "Start differs 1.4 s" Red
2 A and B both have a finish, more than 1.0 s apart "Finish differs 2.5 s" Red
3 B has a start or finish that A doesn't "A start / finish missing" Red
4 A has a start or finish that B doesn't "B start / finish missing" Amber
5 Statuses differ (DNS / DNF / DSQ in one, not the other) "Status A: DNF / B: –" Red
6 A starter or finisher used Flag for review, not yet resolved "⚑ Flagged for review" Red

A flag disappears by itself as soon as its cause is gone (for example, A's finish is set to match B's).

5. Points to confirm before race day (the logic)

  1. A is the only official record. Corrections go into A; changing B is allowed but has no public effect. OK?
  2. Matching A to B clears the flag by itself. There is no need to Resolve as well. OK?
  3. Resolve means "A is right as it stands". It covers all the crew's current differences at once, and any later change to A or B undoes it. OK?
  4. Tolerance is 1.0 s for starts and finishes (more than 1.0 s apart is flagged). Keep, or change?
  5. A finish with no start yet (allowed since the snag fixes) shows as "A start missing" only once B has a start. If neither A nor B ever gets a start, the crew has no race time and isn't flagged. Race Configuration / Results show it without a time. Should "finish but no start in A or B" be a 7th rule?
  6. Every change needs a typed reason, even copying B's time. Keep, or allow "Use B's" without a reason?

Snagging brief (club test)reference

The four snags from Thursday's club test and how they were fixed.

Test: Thu 22 Oct 2026, evening, at the club, several officials on their own phones and iPads Reported by: the race admin, from the officials at the test · Written: 22 Oct 2026, 21:50 Status: agreed, built and tested on 22 Oct. The changes this makes to the design brief are listed in section 3.

1. The snags

# Page What happened at the test Why it matters Fix (what "done" looks like)
S-1 Starter and Finisher A few seconds after a START or FINISH, the page scrolled by itself: to the next crew on Starter, and Finisher moved finished rows away. Several people hit the wrong crew because the list moved just as their finger came down. A wrong-crew tap gives a wrong time, and nobody may notice. The page never scrolls or reorders by itself. Only the person holding the phone scrolls. The "next crew" highlight stays, but nothing moves. The jump box stays, because it only scrolls when you ask it to.
S-2 Starter and Finisher After a tap, the toast ("157 started 10:02:13.4") and the amber "Sending 3…" light both appeared. But on a weak connection the button didn't change to Undo until the server had confirmed it ("All saved"). People said "the button isn't registering" and some tapped again. The tap was stored on the phone, but the screen didn't say so. That leads to second taps, Replace prompts and doubt. The button changes to Undo the moment the tap is accepted on the phone, whatever the connection. The time shows on the row at once. The light still shows Sending / All saved for the upload. The 2 s double-tap guard (F-S12) still applies. If the page is reopened while taps are still waiting to send, those rows still show as done.
S-3 Finisher A crew's FINISH button only appeared once the Finisher phone had received that crew's start. If the start phone was out of signal, the start could arrive after the boat crossed the line, and the finisher would have no button to tap. You can't time a finish you can't tap. Starts and finishes have to be independent. Every crew has a FINISH button from the beginning of the race, whether or not a start has been received. The row shows "Started 10:02:13" when a start is known and "No start received yet" when not. A finish with no start yet is saved normally, and the race time works itself out when the start arrives. (Race Adjudication flags it if the start never arrives.)
S-4 Finisher After FINISH, the row moved down to a "Finished" section below the crews still racing. Under race pressure the finisher loses their place, and the next button shifts under their thumb (same harm as S-1). One list in bow-number order that never reorders. A finished row stays exactly where it was, turns green, shows the finish time and race time, and shows Undo where FINISH was. DNS / DNF / DSQ / Withdrawn rows also stay in place, showing their status.

2. Checks before it goes back out

  • Automated (local test copy): no scroll movement after a tap, on either page. The button becomes Undo straight after the tap with the server deliberately not answering. On reload with taps still waiting, those rows still show Undo. The Finisher has a FINISH button for a crew with no start. Bow order is unchanged after a finish. Earlier regression tests still pass.
  • Friday test script: steps added for each snag (T-24 to T-27). The club test is the real proof, especially S-2 on a weak signal.

Part C — How a time-trial head race is timed

A head race is a race against the clock. Crews are marshalled in bow-number order above or below the start, then sent off one at a time, usually a few seconds to a few tens of seconds apart. They race the course and cross the finish line — often not in the order they started, because faster crews overtake.

Each crew therefore has two moments that matter:

  1. Start time — the instant the crew crosses the start line at racing pace.
  2. Finish time — the instant the crew's bow crosses the finish line.

Race time = finish time − start time. Results rank crews by race time: overall within a division, and within each event.

What makes it work in practice:

  • One clock. Both times must come from the same time reference, or every race time carries the gap between the two clocks. Useful fact: if the start phone and finish phone disagree by a fixed amount, every crew's time is wrong by that same amount — so the order of finish is still right and only the absolute times shift. It becomes a real problem only if the phone changes mid-division, or a crew's start and finish are logged on a mixture of phones.
  • One tap per event, no thinking. The starter and finisher are outside, often cold, sometimes in the rain, with gloves on. Buttons have to be big and the right crew has to be easy to find.
  • Bunching at the finish. Two or three crews can cross within a second or two. The finisher needs a way to capture the time first and work out which crew it was second.
  • Mistakes get made. A wrong tap has to be fixable without losing the original record.
  • Signal drops. River banks are poor for mobile data. A tap must be safe on the phone the instant it's made, and sync when it can.
  • Redundancy. Raceclocker was set up as two independent races (A and B), each with its own starter and finisher. If one phone dies or someone mis-taps, the other set of times stands. This brief keeps that pattern.
  • Statuses. Not every crew finishes: DNS (did not start), DNF (did not finish), DSQ (disqualified). These go in the results with no time.

Part F — Technical requirements

F1. Hosting and constraints (what's already fixed)

  • dewhurst.tech is a static site on GitHub Pages, published from the site's publishing folder with GitHub Desktop. There is no server of its own.
  • The repository behind GitHub Pages is public. Anything in the page code — including any keys — is readable by anyone. Security has to come from the backend service, not from hiding things in JavaScript.
  • The site's existing form collector (Web3Forms) only sends emails. It can't store or share live timing data, so it is not suitable here.
  • So the timing pages must be plain HTML, CSS and JavaScript, talking to a hosted backend service from the browser.

F2. Backend — recommendation and fallback

Option How it works For Against
1. Firebase (Cloud Firestore + Firebase Auth) — recommended Free Google service. The JavaScript library loads from Google's CDN. Data syncs live between phones. Built-in offline mode: taps are stored on the phone and sent when signal returns — exactly the river-bank problem. Live updates to Results with no polling. Real sign-in. Free tier is ample (88 crews × 2 instances is a few hundred writes). Set-up is about 20 minutes in the Firebase console. New account/project to create. Data lives in Google Cloud, not in the race spreadsheet — needs the CSV export to get it out.
2. Google Apps Script + Google Sheet A small script published as a web app, writing each tap as a row in a Google Sheet. Data lands straight in a spreadsheet. No new service. No offline mode — the "queue and retry" would have to be built from scratch. 1–3 s round-trip per write. Not live; Results has to poll. More to go wrong in three days.

Recommendation: Option 1. The offline handling alone is worth it. If Option 2 were chosen, every functional requirement would still stand, with a local queue (T-T4) and polling added.

F3. Data model (Firestore)

config/race              { name, date, divisions: { "1": "10:00", "2": "11:30", "3": "13:30" }, updatedAt }
entries/{bow}            { bow, event, crew, club, division, status, notes, updatedAt, updatedBy }
taps/{autoId}            { instance: "A"|"B", bow | null, kind: "start"|"finish"|"mark"|"void"|"status",
                           value (status text, or id of tap being voided),
                           tDevice (ms, phone clock), offset (ms), tCorrected (ms),
                           deviceId, user, createdAt (serverTimestamp) }
timings/{instance}       { "151": { start: tCorrected, startTap: id, finish: …, finishTap: id, status: … }, … }
  • taps is append-only — the audit trail. Nothing is ever deleted or overwritten in it.
  • timings/A and timings/B are one document each, holding the current start/finish/status per bow. Every tap writes both its taps record and the matching field in timings/{instance} in a single batched write (works offline).
  • Results reads timings/A or timings/B plus entries — a handful of document reads per viewer, which keeps a busy Results page well inside the free tier.
  • Race time is calculated in the browser from finish − start, not stored, so a corrected start or finish automatically corrects the race time. (Raceclocker stores it; we don't need to.)

F4. Timing and clocks

ID Requirement
T-T1 Capture the tap time with Date.now() inside the click handler, before anything else runs. Use pointerdown, not click, to save the ~100–300 ms a click event adds on touch screens.
T-T2 Server offset: on page load and every 5 minutes, measure the phone's clock against server time (write a doc with serverTimestamp(), read it back, take the midpoint of the round-trip). Store offset; tCorrected = tDevice + offset. Show the offset in a small settings panel.
T-T3 If the measured offset is more than ±2 s, show an amber warning: "This phone's clock is X s out — check Settings › Date & time › Automatic". Never block a tap because of it.
T-T4 Every tap is written to the phone's local storage first, then sent. (Firestore's offline persistence does this; turn it on with persistentLocalCache.) Closing the tab or the phone sleeping must not lose a tap.
T-T5 Times are stored as UTC milliseconds and displayed in UK local time (BST ends Sun 25 Oct, so Saturday is still BST — the browser handles it). Display to tenths of a second.
